# Частые вопросы о ML-Loop

По этому проекту мне тоже задавали много вопросов — от выбора LoRA до метрик качества обучения. Собрал самые частые здесь, чтобы не повторяться на каждом собеседовании.

---

## Q: Почему LoRA, а не full fine-tuning?

**A:** Full fine-tuning требует GPU и гигабайт RAM на хранение весов. У меня обучение идёт на GitHub Actions CPU с 7 GB RAM — full fine-tune Qwen2.5-0.5B туда физически не влезет.

LoRA (Low-Rank Adaptation) дообучает маленькую «надстройку» весов вместо всей модели: r=8, alpha=16. Это даёт:
- Обучение за 4 минуты на CPU вместо часов на GPU
- Адаптер ~10 МБ вместо ~1 ГБ полной модели
- Качество сопоставимо с full fine-tuning на моих данных

**Trade-off:** на очень специфичных доменах LoRA слабее full fine-tune, но для моих задач разница несущественна.

---

## Q: Что такое eval loss и почему 3.87 → 3.77 это хорошо?

**A:** Eval loss — ошибка модели на проверочной выборке, которую модель не видела при обучении. Чем ниже — тем лучше модель предсказывает следующий токен.

3.87 → 3.77 = модель стала лучше. Это не «большой» прогресс, но цикл идёт автоматически каждую неделю — кумулятивно даёт существенный прирост. Важно направление (снижение), а не абсолютное значение.

**Почему не accuracy:** для языковых моделей eval loss — стандарт, потому что «правильного» следующего токена нет, есть распределение вероятностей.

## Q: Почему GitHub Actions, а не свой GPU-сервер?

**A:** Экономия. GPU-сервер (A100) — $3-10/час в облаке, за месяц ежедневного обучения — сотни долларов. GitHub Actions даёт 2000 бесплатных минут CPU/месяц, обучение занимает 4 минуты. Итого — бесплатно.

**Trade-off:** CPU медленнее GPU в 10-50 раз, поэтому я ограничен моделью 0.5B. Для 7B+ придётся платить за GPU или поднимать свой runner.

---

## Q: Почему Qwen2.5-0.5B, такая маленькая модель?

**A:** Из-за ограничений CPU GitHub Actions. 0.5B = ~1 ГБ весов, влезает в 7 GB RAM с запасом под LoRA.

Модели побольше на CPU:
- 7B требует ~14 GB RAM — Actions упадёт с OOM
- 13B требует ~26 GB RAM — тем более

**Когда перейду на 7B+:** свой GPU-сервер, арендованный GPU-раннер или QLoRA (4-bit квантизация снижает требования в 4 раза).

**Trade-off:** 0.5B слабее держит контекст, но цикл работает автономно и бесплатно.

---

## Q: Зачем LLM-куратор (Groq Llama 3.1), почему не регулярки?

**A:** Регулярки отсекают только явный мусор (URL, HTML-теги). Но в сырых данных с Reddit/HN/Wiki есть токсичные комментарии, спам, PII, галлюцинации других LLM.

LLM-куратор оценивает качество как человек: «этот текст полезный, а этот — мусор». Groq Llama 3.1 за $0.59/млн токенов обрабатывает 11 000 документов за ~$0.01.

**Trade-off:** зависимость от Groq API. Если урежут — fallback-список (Together AI, OpenRouter, локальный Ollama).

---

## Q: Что такое shingle-дедупликация и зачем порог 50%?

**A:** Shingle-дедуп — удаление почти одинаковых текстов через n-граммы. Разбиваю текст на шинглы (последовательности из N слов), считаю долю общих между двумя текстами. Если >50% — один удаляю.

**Зачем:** дубли в данных = модель переобучится и будет повторять одни и те же фразы.

**Почему 50%:**
- 80% — слишком строго, удалю полезные перефразирования
- 30% — слишком мягко, оставлю дубли
- 50% — баланс: удаляю явные копии, сохраняю перефразы

**Trade-off:** часть уникальных текстов теряется. Для моих объёмов приемлемо.

---

## Q: Почему данные в Git (jsonl), а не в базе?

**A:** Батчи маленькие (0.5-13 КБ), Git даёт:
- Версионность: вижу какие данные были в каждом цикле
- Бесплатный бэкап (GitHub реплицирует)
- Workflow-as-code: инфраструктура в репозитории
- Простоту: git pull — данные на месте

**Когда пойду в БД/HF Datasets:** объём 100к+ строк, конкурентная запись, сложные запросы.

**Trade-off:** Git не подходит для больших объёмов. Для текущих данных оверхеда нет.

## Q: Как устроен jsonl и почему не CSV?

**A:** JSONL = JSON Lines, каждая строка — отдельный JSON-объект:

{"text": "Как настроить Asterisk для SIP-звонков", "source": "hackernews"}
{"text": "История Википедии про телеграфию", "source": "wikipedia"}

**Почему не CSV:**
- CSV плохо работает с текстом с запятыми, кавычками, переносами
- В JSONL экранирование автоматическое
- JSONL — стандарт ML-датасетов (HuggingFace)

**Почему не один большой JSON:** JSONL позволяет дописывать батчи построчно, не переписывая файл. Критично для циклического сбора.

## Q: Что если Reddit блокирует IP?

**A:** Fallback: если Reddit вернул 403 или timeout, сбор продолжается из HackerNews + Wikipedia. Цикл не падает.

Реализовано в n8n workflow: каждый источник в отдельной ноде с try-catch. Упал источник — данные идут из оставшихся.

**Важно:** это graceful degradation, не поломка. Цикл работает с меньшим объёмом.

**Митигация полного отказа:** мониторинг в Telegram (данных < 50 — алерт) + ручной Run workflow позже.

## Q: Что если Groq урежут free tier?

**A:** Митигации:
1. Fallback-список провайдеров: Together AI, OpenRouter, локальный Ollama
2. Мониторинг: Telegram-алерт при 429 или росте latency
3. Буферизация: данные копятся в Git, обучение запускается позже через другой провайдер

**Реальность:** free tier — осознанный риск демо-проекта. Для production — платный API или self-hosted LLM.

## Q: Что такое «адаптер» на HuggingFace?

**A:** Адаптер — результат LoRA-обучения: файл ~10 МБ с дообученными весами. Не полная модель, а надстройка к базовой Qwen2.5-0.5B.

**Как использовать:** PeftModel.from_pretrained(base_model, "SergIS777/ml-loop-adapter")

**Преимущество:** множество адаптеров под разные домены, базовая модель одна.

## Q: Как проверял, что обучение реально улучшило модель?

**A:** Три уровня:
1. Eval loss снизился (3.87 → 3.77) — метрика на проверочной выборке
2. До/после: базовая модель генерирует общий стиль, после — адаптируется к стилю моих данных
3. Ручная проверка: 10 сэмплов, сравниваю «до» и «после»

**Почему нет BLEU/ROUGE:** требуют reference text, которого нет (обучаю на корпусе, не на парах).

## Q: Как тестировал систему?

**A:** Два уровня:

**1. Unit-тесты (pytest):** tests/test_data.py — pipeline очистки, shingle-дедуп, курация.

**2. Production-тестирование:** цикл работает автономно каждую неделю, eval loss не растёт, адаптер публикуется на HF, Telegram-отчёты после каждого цикла.

**Чего НЕТ:** тестов на train/lora_train.py — требуют mock HF Hub, ROI низкий для single-dev; интеграционных тестов всего цикла — долго и дорого. Это осознанное решение, обучение проверяется production-метриками.

## Q: Что если нужно обучать под несколько доменов?

**A:** Текущая архитектура — один адаптер на общий стиль. Для нескольких доменов:

**Вариант 1:** матрица «домен → адаптер»: отдельный batch, отдельный цикл, выбор адаптера в runtime.

**Вариант 2:** один адаптер на смешанных данных — проще, но качество ниже.

**Выбор:** production — вариант 1, демо — один адаптер.

## Q: Как мониторить, что цикл жив?

**A:** Telegram-отчёты после каждого цикла:
- Количество документов
- Было обучение или мягкий скип
- Eval loss до/после
- Ссылка на адаптер
- Время выполнения

**Алерты:** данных < 50 → алерт; eval loss вырос → алерт «дрейф»; цикл упал → алерт от Actions.

**Принцип:** молчание системы = она мертва. Всегда есть сигнал.

## Q: Какие альтернативы твоей архитектуре?

**A:** Три основных:

**1. HF AutoTrain:** managed fine-tuning, но платно и без кастомизации. У меня полный контроль.

**2. Собственный GPU + Ollama/vLLM:** локальное обучение без API, но дорогая инфраструктура.

**3. Платные ML-платформы:** быстрее старт, но vendor lock-in и стоимость.

**Почему мой вариант:** баланс контроля и стоимости, production-цикл без платных сервисов.

## Q: Что если нужно обучать модель 7B+?

**A:** Текущая архитектура ограничена CPU Actions (7 GB RAM). Для 7B+:

**Вариант 1:** арендовать GPU-раннер (Lambda Labs, RunPod) + self-hosted runner для Actions.

**Вариант 2:** QLoRA (4-bit) — требования к RAM в 4 раза меньше, 7B влезает на CPU.

**Вариант 3:** свой GPU-сервер — полный контроль, но $5-10k капитальных затрат.

**Выбор:** production — GPU в облаке, демо — QLoRA.

## Q: Какие метрики отслеживаешь в цикле?

**A:** Четыре группы:

## Q: Какие антипаттерны ты избегаешь?

**A:** Три главных:

**1. Переинженеринг:** не строю сложную архитектуру «на будущее». Сначала простая версия, усложняю когда упираюсь в потолок.

**2. Молчаливые падения:** каждая ошибка логируется и алертит. Цикл упал — узнаю через минуту, а не через неделю.

**3. Зависимость от одного источника:** Reddit заблокировал IP — система не падает, собирает из HN + Wiki.

**Принцип:** надёжность важнее изящества архитектуры.

## Q: Что самое сложное было при разработке?

**A:** Две вещи:

**1. Баланс скорости и качества обучения:** меньше LoRA-ранг — быстрее обучение, но хуже качество. Эмпирически подобрал r=8/alpha=16.

**2. Edge cases в данных:** Reddit отдаёт битые посты с HTML, Wikipedia — служебные страницы (Talk:, User:), HN — комментарии-вопросы без ответов. Каждый edge case — отдельная обработка в train/data.py.

**Принцип:** 80% времени уходит на граничные случаи, а не на основную логику.
